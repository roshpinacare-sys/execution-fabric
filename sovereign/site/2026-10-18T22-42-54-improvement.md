# מדריך תפעול שרשרת-האמת: בניית ואימות בלוקים חדשים

## סקירה כללית
מדריך זה מסביר את התהליך המלא להוספת בלוק חדש לשרשרת-האמת, כולל הכנת הנתונים, יצירת הבלוק, אימות תקינותו, ושילובו בשרשרת. המדריך מיועד למפתחים ומנהלי מערכת העובדים עם שרשרת-האמת.

## דרישות מוקדמות
- גישה ל-API של שרשרת-האמת (`/api/ledger`)
- הבנת בסיסית של מבנה בלוקים ו-hash chains
- הרשאות כתיבה לשרשרת

## תהליך הוספת בלוק חדש

### 1. הכנת הנתונים
כל בלוק חייב לכלול את הרכיבים הבאים:

```json
{
  "timestamp": "2026-10-18T22:42:17.332Z",
  "previousHash": "hash_of_previous_block",
  "transactions": [
    {
      "id": "unique_tx_id",
      "type": "transfer|update|create",
      "data": {"...": "..."}
    }
  ],
  "metadata": {
    "creator": "system_user",
    "version": "1.0.0"
  }
}
```

**הערות חשובות:**
- `timestamp` חייב להיות בפורמט ISO 8601
- `previousHash` חייב להתאים ל-hash של הבלוק האחרון בשרשרת
- כל טרנזקציה חייבת לכלות ID ייחודי

### 2. יצירת ה-Hash
לאחר הכנת הנתונים, יש לחשב את ה-hash של הבלוק:

```javascript
const crypto = require('crypto');
const blockData = JSON.stringify(blockData);
const blockHash = crypto.createHash('sha256').update(blockData).digest('hex');
```

ה-hash נוצר מכל הנתונים בבלוק (למעט ה-hash עצמו).

### 3. אימות תקינות
לפני הוספת הבלוק לשרשרת, יש לבצע אימות:

1. **אימות תקינות נתונים:**
   - בדיקה שכל השדות חובה קיימים
   - בדיקת תקינות פורמט ה-timestamp
   - אימות שכל ה-ID של הטרנזקציות ייחודיים

2. **אימות רציפות השרשרת:**
   - השוואת `previousHash` ל-hash האחרון בשרשרת
   - בדיקה שאורך ה-hash הוא 64 תווים (hexadecimal)

3. **אימות חתימה (אם נדרש):**
   - בדיקת חתימת היצרן על פי ה-metadata

### 4. הוספה לשרשרת
אם האימות עבר בהצלחה, ניתן להוסיף את הבלוק:

```bash
curl -X POST \
  http://api.example.com/api/ledger/block \
  -H 'Content-Type: application/json' \
  -d '{
    "block": { ... },
    "hash": "calculated_hash"
  }'
```

### 5. אישור וסנכרון
לאחר ההוספה:
1. המערכת מאשרת את קבלת הבלוק
2. הבלוק מתווסף לכל העותקים של שרשרת-האמת
3. ה-hash של הבלוק החדש משמש כ-`previousHash` לבלוק הבא

## בדיקות תקינות לאחר הוספה

1. **בדיקת גישות:**
   ```bash
   curl http://api.example.com/api/ledger/validate
   ```
   ה-API מחזיר את מצב השרשרת (תקינ/לא תקינ) ואת הבלוק הראשון שבו נמצא שגיאה (אם קיימת).

2. **בדיקת אורך השרשרת:**
   ```bash
   curl http://api.example.com/api/ledger/length
   ```
   מחזיר את מספר הבלוקים הנוכחי בשרשרת.

## אופטימיזציה ושיטות מומלצות

1. **גודל בלוקים:**
   - מקסימום גודל מומלץ: 1MB
   - אם יש יותר מדי טרנזקציות, יש לחלק למספר בלוקים

2.תדירות יצירה:
   - בלוקים חדשים נוצרים כל 30 שניות (בממוצע)
   - בתקופות עומס, ניתן להגדיל עד 60 שניות

3.אחסון:
   - שמור עותק מקומי של ה-10 בלוקים האחרונים לצורך אימות מהיר
   - השתמש ב-Pruning לבלוקים ישנים מ-1000 בלוקים

## טיפול בשגיאות נפוצות

| שגיאה | פתרון |
|--------|--------|
| "Invalid previous hash" | בדוק את ה-hash של הבלוק האחרון | 
| "Duplicate transaction ID" | ודא שכל ה-ID ייחודיים | 
| "Block size exceeded" | צמצם את מספר הטרנזקציות | 
| "Invalid timestamp format" | ודא שה-timestamp בפורמט ISO 8601 | 

## ניטור ודיווח
לאחר הוספת בלוק, יש לבדוק את מצב השרשרת בממשק הניטור:

1. גש ל-`/api/ledger/metrics`
2. בדוק את מדדי הביצוע:
   - `block_creation_time` - זמן יצירת בלוק ממוצע
   - `validation_success_rate` - אחוז האימותים המוצלחים
   - `chain_depth` - עומק השרשרת
