# לקחים מעשיים: ניהול תקציב התפתחות שעתי ברשת אוטונומית

> **הקשר**: הרשת דיווחה על "תקציב-ההתפתחות השעתי מוצה (12/12)" — אירוע שגרם לעצירת פעימות התפתחות למשך שעה שלמה. המסמך הזה מרכז את הלקחים התפעוליים לזיהוי מוקדם, ניטור רציף והתאוששות מהירה.

---

## 1. זיהוי מוקדם — סימנים מקדימים

| סימן | מקור ניטור | פעולה מיידית |
|-------|------------|---------------|
| `evolution.budget.remaining ≤ 2` | `/api/evolution` (שדה `budget.remaining`) | הפעל התראת "תקציב נמוך" בקונסולה |
| קצב בקשות `/api/evolution` יורד ב־>30% ב־5 דקות | מדדי רשת (`/api/metrics` → `evolution.request_rate`) | בדוק האם עורקי-הלב תקועים |
| משימות `kind=self-origin` נערמות ב־`pending` | לוח משימות (Dispatch → Workers) | תעדף ידנית משימה אחת לשחרור צוואר-בקבוק |

**כלל אצבע**: אם `budget.remaining == 0` — הרשת **לא** תייצר שיפורים חדשים עד תחילת השעה הבאה. זה לא באג — זה מנגנון הגנה.

---

## 2. ניטור רציף — לוח מחוונים מינימלי

הוסף לקונסולת המפעיל (או לסקריפט `watch-evolution.sh`) את התצוגה הבאה:

```bash
# רענון כל 30 שניות
watch -n 30 'curl -s /api/evolution | jq "{budget: .budget, rate: .request_rate_5m, pending: .pending_self_origin}"'
```

**שדות קריטיים**:
- `budget.used / budget.limit` — ניצול נוכחי
- `budget.reset_at` — timestamp איפוס הבא (ISO8601)
- `request_rate_5m` — בקשות/דקה ב־5 דקות אחרונות
- `pending_self_origin` — משימות התפתחות עצמית ממתינות

---

## 3. התאוששות מהירה — נוהל "שעה אבודה"

כשהתקציב מוצה (`remaining == 0`):

1. **אל תנסה לכפות** — בקשות `/api/evolution` יחזירו `429 Budget Exhausted` עד `reset_at`.
2. **נצל את ההפסקה** — הרץ ביקורות ידניות על `openHighs` (כרגע 37 פתוחים).
3. **הכן "מנות פתיחה"** — כתוב 2–3 הצעות `PROPOSAL` מוכנות להגשה ברגע שהשעה מתאפסת.
4. **עקוב אחרי איפוס** — ב־`reset_at` צפה ל־`budget.remaining == 12` ו־`request_rate_5m` קופץ.

**תבנית הודעת התאוששות** (להדבקה ביומן עורקי-הלב):
```
[RECOVERY] Budget reset at {{reset_at}}. Remaining: 12. Queued proposals: {{N}}. Resuming evolution pulse.
```

---

## 4. מניעה — התאמת קצב יזומה

| מצב | אסטרטגיה |
|------|----------|
| שגרה (budget > 6) | קצב רגיל — 1 שיפור/5 דקות |
| אזהרה (budget 3–5) | האט ל־1 שיפור/10 דקות; תעדף `HIGH` בלבד |
| קריטי (budget ≤ 2) | הקפא ייצור חדש; התמקד בניקוי `openLoops` |

**יישום בקוד** (פסאודו-לוגיקה לעורק-ההתפתחות):
```python
def next_pulse_interval(budget_remaining: int) -> int:
    if budget_remaining >= 6: return 300      # 5 דק'
    if budget_remaining >= 3: return 600      # 10 דק'
    return 0  # הקפאה — המתן לאיפוס
```

## 5. רשימת צ'ק-ליסט שבועית למפעיל

- [ ] ודא ש־`budget.limit` תואם את מדיניות הרשת הנוכחית (כרגע 12/שעה)
- [ ] בדוק שאין דליפת בקשות כפולות (idempotency keys בשימוש?)
- [ ] סקור `openHighs` — האם ממצאים חמורים תקועים בגלל תקציב?
- [ ] אשר ש־`reset_at` מסונכרן עם שעון UTC (לא שעון מקומי)
- [ ] תעד אירועי "שעה אבודה" ביומן הרשת — חפש תבניות (יום/שעה קבועים?)

---

## 6. מדד הצלחה — "זמן להתאוששות מלאה"

**הגדרה**: מרגע `budget.remaining == 0` עד לרגע שבו `request_rate_5m` חוזר ל־≥80% מהממוצע השעתי הרגיל.

**יעד**: < 15 דקות לאחר איפוס התקציב.

**מעקב**: רשום כל אירוע ב־Ledger עם תג `budget_recovery` — מאפשר ניתוח מגמות חודשי.

---

> **שורה תחתונה**: תקציב התפתחות שעתי הוא **מנגנון ויסות בריא**, לא תקלה. המפתח הוא נראות (דאשבורד), התראה מוקדמת (≤2), ונוהל התאוששות מתורגל. כשהשעה מתאפסת — הרשת צריכה לזנק קדימה, לא לגמגם.
