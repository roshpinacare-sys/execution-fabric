# שאלות-ותשובות: אבחון ותיקון כשלים ברשת

> **למי זה מיועד:** מפתחים ומפעילים שצריכים להבין *למה* משימה נכשלה ו*איך* לתקן בלי לפגוע בשלמות הלדג'ר.

---

## 1. משימה מופיעה במחלקה "unknown" — מה זה אומר ואיך מתקנים?

**סימפטום:** בלוח המשימות או בשרשרת-אמת רואים משימות עם `department: "unknown"` (כרגע 25 מקרים כאלה).

**סיבה-שורש נפוצה:** ה-worker לא דיווח `department` בעת יצירת המשימה, או שה-handler לא מיפה נכון את סוג המשימה למחלקה.

**אבחון מהיר (קונסולה):**
```bash
# בדיקת בלוקים אחרונים עם department=unknown
curl -s /api/metrics | jq '.recentBlocks[] | select(.department=="unknown") | {hash, taskId, department, workerId, timestamp}'
```

**תיקון:**
1. אתר את ה-worker שייצר את המשימה (`workerId` מהבלוק).
2. ודא שה-worker שולח `department` תקין ב-payload ההרשמה/ביצוע.
3. אם ה-worker תקין — בדוק את ה-dispatcher: האם הוא ממפה `taskType` → `department` נכון?
4. הוסף ולידציה ב-dispatcher: דחה משימות בלי `department` עם שגיאה ברורה.

**מניעה:** הוסף test אוטומטי שמוודא שכל taskType ממופה למחלקה קיימת.

## 2. פער בשרשרת-אמת (hash-chain gap) — איך מאתרים ומתקנים?

**סימפטום:** `chain.verify()` מחזיר false, או שבלוק צפוי חסר ברצף.

**אבחון:**
```bash
# בדיקת שלמות מלאה
curl -s /api/metrics | jq '.chain.integrity'
# פירוט בלוקים בעייתיים
curl -s /api/metrics | jq '.chain.gaps // []'
```

**סיבות נפוצות:**
- כתיבה מקבילה שלא עברה קונצנזוס
- קריסת worker באמצע כתיבת בלוק
- באג ב-hash calculation (שדה חסר/שונה)

**תיקון (זהיר!):**
1. **אל תמחק/תשנה בלוקים קיימים** — זה שובר את ההיסטוריה.
2. זהה את הבלוק האחרון התקין (`lastValidHash`).
3. אם הפער קטן (1-2 בלוקים) ויש לך את הנתונים המקוריים — כתוב בלוקי-השלמה (`kind: "recovery"`) שמצביעים על `lastValidHash` ומכילים את הנתונים החסרים.
4. אם הפער גדול — הפעל `chain.rebuildFrom(lastValidHash)` רק אחרי גיבוי מלא ותיעוד סיבה.

**כלל ברזל:** כל תיקון שרשרת נרשם כבלוק חדש עם `kind: "chain-repair"` וסיבה מפורטת.

## 3. משימה נתקעת ב-RUNNING / TIMEOUT — מה בודקים?

**סימפטום:** משימה נשארת בסטטוס `RUNNING` מעבר ל-SLA, או מסתיימת ב-`TIMEOUT`.

**רשימת בדיקה (לפי סדר עדיפות):**
1. **Worker חי?** `curl /api/census | jq '.workers[] | select(.id=="<workerId>") | {id, status, lastHeartbeat}'`
2. **לוגי worker:** חפש שגיאות בקונסולת ה-worker או ב-`/api/arsenal` → logs.
3. **תלות חיצונית:** האם המשימה מחכה ל-API חיצוני, DB, או משימה אחרת?
4. **הגדרת timeout:** האם `timeoutMs` ב-task spec מתאים למורכבות האמיתית?
5. **זליגת זיכרון/CPU:** `curl /api/metrics | jq '.system.resources'`

**תיקון מהיר:**
- אם worker מת — סמן משימה כ-`FAILED` עם סיבה `worker-lost`, ה-dispatcher יתזמן מחדש.
- אם תלות חיצונית — הוסף retry עם backoff ב-task handler.
- אם timeout קצר מדי — עדכן `timeoutMs` ב-spec (שינוי קונפיגורציה, לא קוד).

## 4. ביקורת-עומק נכשלת שוב ושוב ("סולם-מוצה") — מה עושים?

**מצב:** כל המועמדים לתיקון נדחו בכנות — הניסיון החוזר הוא החלטת-בעלים.

**גישה מומלצת:**
1. **תעד את הכשלון** — כתוב בלוק `kind: "audit-failure"` עם פירוט מה נוסה ולמה נדחה.
2. **צמצם היקף** — במקום לתקן הכל, תקן *חלק אחד קטן* שניתן לאמת בנפרד.
3. **הפרד חששות** — האם הבעיה בקוד, בקונפיגורציה, בנתונים, או בתהליך?
4. **בקש חוות-דעת שנייה** — פתח HIGH finding עם תיוג `needs-review` והקשר מלא.

**דוגמה לתבנית HIGH finding:**
```yaml
kind: HIGH
area: deploy-scripts
issue: spread-env / SOVEREIGN_VAULT_SECRET detection
attempted:
  - grep patterns (false positives)
  - AST parsing (missed dynamic requires)
  - manual audit (time-boxed, incomplete)
blocker: "no reliable automated detection without false negatives"
next: "design allowlist-based scanner with owner approval"
```

## 5. 16 ממצאי-HIGH פתוחים — איך מתעדפים ולא טובעים?

**עיקרון:** לא הכל דחוף. השתמש במטריצה:

| חומרה × דחיפות | פעולה |
|---|---|
| גבוהה × גבוהה | תיקון מיידי (blocking) |
| גבוהה × נמוכה | תזמן לספרינט הקרוב |
| נמוכה × גבוהה | workaround זמני + תיעוד |
| נמוכה × נמוכה | סגור כ-wontfix או תיעוד ל-tech-debt |

**כלי עזר בקונסולה:**
```bash
# רשימת HIGH פתוחים עם עדיפות
curl -s /api/evolution | jq '.highFindings[] | select(.status=="open") | {id, title, severity, urgency, ageDays}' | sort -k4 -nr
```

**טיפ:** קבע "שעת HIGH" שבועית קבועה (30 דק') — עיבוד מרוכז עדיף על פיזור.

## 6. טעויות נפוצות — ומה לעשות במקום

| טעות | למה זה מזיק | חלופה נכונה |
|---|---|---|
| מחיקת בלוקים "לתקן" שרשרת | שובר אימות היסטורי, מאבד אמון | בלוקי-השלמה (`recovery`) עם הפניה לבלוק אחרון תקין |
| התעלמות מ-`unknown` department | מסתיר בעיות ניתוב, פוגע באנליטיקה | ולידציה ב-dispatcher + התראה אוטומטית |
| הגדלת timeout בלי לחקור סיבה | מסווה בעיות ביצועים/ארכיטקטורה | פרופילינג → זיהוי צוואר-בקבוק → תיקון שורש |
| ניסיון חוזר לאותו תיקון שנדחה | מבזבז מחזורי רשת, מייצר רעש | תיעוד כשלון + צמצום היקף + גישה חדשה |
| טיפול ב-HIGH לפי סדר הגעה | דחוף דוחק חשוב | מטריצת חומרה×דחיפות + שעה שבועית קבועה |
