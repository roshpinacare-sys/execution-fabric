# ממשק הרשאות מבוסס-תפקידים לשערי-הפעלה של רכיבי-צד

# הצעה: ממשק הרשאות מבוסס-תפקידים לשערי-הפעלה של רכיבי-צד

## הבעיה
כיום כל רכיב צדדי (sidecar) שנרשם בשער ההפעלה זמין לכל משתמש/תהליך שיש לו גישה לממשק. אין הפרדה בין:
- מפעילים אנושיים (מפתחים, סוקרים, אוטומציה)
- תהליכי מערכת (עובדי-לב, סורקים, בודקים)
- סביבות (פיתוח, סטייג׳, פרודקשן)

הדבר יוצר סיכון: הפעלה מקרית או זדונית של יכולות הרסניות (מחיקת נתונים, פריסת גרסה, שינוי תצורה) על ידי גורם לא מורשה.

## הפתרון המוצע
ממשק הרשאות **מינימלי, הצהרתי וניתן-להרחבה** שמורכב משלושה חלקים:

### 1. מודל נתונים (JSON Schema)
```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "properties": {
    "roles": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["id", "name", "permissions"],
        "properties": {
          "id": {"type": "string"},
          "name": {"type": "string"},
          "permissions": {
            "type": "array",
            "items": {
              "type": "object",
              "required": ["capabilityId", "actions"],
              "properties": {
                "capabilityId": {"type": "string"},
                "actions": {
                  "type": "array",
                  "items": {"type": "string", "enum": ["invoke", "configure", "observe"]}
                }
              }
            }
          }
        }
      }
    },
    "bindings": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["subject", "roleId"],
        "properties": {
          "subject": {"type": "string", "description": "מזהה משתמש/שירות/קבוצה"},
          "roleId": {"type": "string"}
        }
      }
    }
  },
  "required": ["roles", "bindings"]
}
```

### 2. נקודת-אכיפה (Enforcement Point)
- **מיקום**: `middleware/authorization.ts` — רכיב ביניים חדש שמתיישב **לפני** שער ההפעלה הקיים.
- **התנהגות**:
  1. מחלץ זהות מבקש מכותרת `X-SAOS-Actor` (או JWT עתידי).
  2. טוען מדיניות מקובץ `config/rbac.policy.json` (נטען פעם אחת, רענון ב-SIGHUP).
  3. בודק התאמה: `subject → role → capabilityId → action`.
  4. אם אין הרשאה — מחזיר `403 Forbidden` עם גוף `{ "error": "RBAC_DENIED", "required": "invoke:log-analyzer" }`.
  5. אם יש הרשאה — מעביר הלאה עם כותרת `X-SAOS-Roles` למידע למטה.

### 3. ממשק ניהול (CLI + API)
| פקודה | תיאור |
|--------|-------|
| `saos rbac policy show` | מציג מדיניות נוכחית | 
| `saos rbac policy validate` | בודק תקינות סכמה | 
| `saos rbac role add <id> <name> --cap <capId>:<action>...` | מוסיף תפקיד | 
| `saos rbac bind <subject> <roleId>` | מקשר נושא לתפקיד | 
| `saos rbac unbind <subject> <roleId>` | מסיר קישור | 
| `POST /api/rbac/policy` | החלפת מדיניות מלאה (דורש תפקיד `rbac:admin`) |

## דוגמה מעשית
**קובץ מדיניות** `config/rbac.policy.json`:
```json
{
  "roles": [
    {
      "id": "developer",
      "name": "מפתח",
      "permissions": [
        {"capabilityId": "log-analyzer", "actions": ["invoke", "observe"]},
        {"capabilityId": "deployment-preview", "actions": ["invoke"]}
      ]
    },
    {
      "id": "release-engineer",
      "name": "מהנדס שחרור",
      "permissions": [
        {"capabilityId": "deployment-preview", "actions": ["invoke", "configure"]},
        {"capabilityId": "production-deploy", "actions": ["invoke"]}
      ]
    },
    {
      "id": "automation-saos",
      "name": "אוטומציה מערכתית",
      "permissions": [
        {"capabilityId": "log-analyzer", "actions": ["invoke"]},
        {"capabilityId": "health-check", "actions": ["invoke", "observe"]}
      ]
    }
  ],
  "bindings": [
    {"subject": "user:alice", "roleId": "developer"},
    {"subject": "user:bob", "roleId": "release-engineer"},
    {"subject": "service:night-shift", "roleId": "automation-saos"}
  ]
}
```

## יתרונות
- **אפס שינוי ליכולות קיימות** — רק עוטף אותן.
- **מדיניות כקוד** — ניתנת לגרסה, ביקורת, PR.
- **ביצועים** — בדיקת הרשאה = חיפוש בזיכרון (Map), <1ms.
- **תאימות** — עובד עם כל מנגנון זיהוי קיים/עתידי.
- **נראות** — כל דחייה נרשמת בלוגר עם `rbac.denied` לאבחון.

## תוכנית מימוש (3 שלבים)
1. **שלב א׳ (ליבה)**: `middleware/authorization.ts` + סכמה + טעינת קובץ + בדיקה בסיסית + לוג דחיות.
2. **שלב ב׳ (CLI)**: פקודות `saos rbac *` לעריכה בטוחה של המדיניות.
3. **שלב ג׳ (אינטגרציה)**: חיבור לשער ההפעלה הקיים — הוספת `X-SAOS-Actor` בבקשות פנימיות, תיעוד למפתחי יכולות חדשות.

## מדדי קבלה
- [ ] בקשת הפעלה ללא כותרת `X-SAOS-Actor` → 401.
- [ ] בקשה עם נושא ללא הרשאה → 403 עם גוף תקני.
- [ ] בקשה מורשית → עוברת עם `X-SAOS-Roles`.
- [ ] טעינת מדיניות לא תקינה → שגיאה ברורה בהפעלה, לא בזמן ריצה.
- [ ] רענון מדיניות ב-SIGHUP בלי הפעלה מחדש.
