# מדריך תפעול: שער-העברה לגיט (/api/handoffs) — מסלול מסירה מבוקר בין עורקים

# מדריך תפעול: שער-העברה לגיט (/api/handoffs)

## למה זה קיים
כשעורק אחד מסיים עבודה שדורשת **המשך טיפול** אצל עורק אחר (למשל: ביקורת שמזהה בעיה → עורק-בנייה שצריך לתקן), אסור שהמידע יאבד בתוך לוגים. שער-ההעברה הוא נקודת-המעבר היחידה: כל העברה נרשמת, מקבלת זהות, מצב, וחתימה בשרשרת-האמת. בלי השער הזה נוצרות "לולאות פתוחות" שאיש לא סוגר.

## מתי לפתוח העברה
- **ממצא דורש תיקון** אצל עורק שאינו זה שגילה אותו.
- **החלטת-בעלים נדרשת** (למשל: ניסיון-חוזר שנדחה בעבר).
- **תלות-חוסמת**: עורק לא יכול להמשיך עד שעורק אחר יספק קלט.
- **מסירת-תוצר**: קובץ/מדריך/הצעה שמוכנים וממתינים לאימוץ.

מתי **לא** לפתוח: כשאפשר לסגור בתוך אותו עורק; כשהמידע כבר קיים בהעברה פתוחה (חפש קודם!).

## מבנה רשומת-העברה
```json
{
  "id": "ho-<חתימה קצרה>",
  "from": "<מזהה-עורק-מקור>",
  "to": "<מזהה-עורק-יעד>",
  "kind": "FIX | DECISION | DEPENDENCY | ARTIFACT",
  "status": "OPEN | ACK | DONE | REJECTED | EXPIRED",
  "priority": "HIGH | NORMAL | LOW",
  "subject": "<שורה אחת>",
  "evidence": ["<קישור-פנימי-לרשומה-בשרשרת>"],
  "createdAt": "<ISO>",
  "dueBy": "<ISO או null>",
  "closedAt": "<ISO או null>",
  "closeReason": "<חופשי, חובה ב-DONE/REJECTED>"
}
```

## מחזור-החיים
1. **OPEN** — המקור פותח. חובה: `to`, `kind`, `subject`, `evidence` אחד לפחות.
2. **ACK** — היעד מאשר קבלה. אם לא אושר תוך חלון-הזמן — ההעברה מסומנת כ"תקועה" במדדי-השער.
3. **DONE** — היעד סיים. חובה `closeReason` שמתאר מה נעשה.
4. **REJECTED** — היעד דוחה. חובה `closeReason` שמסביר למה (לא מספיק "לא רלוונטי").
5. **EXPIRED** — עבר `dueBy` בלי מעבר ל-ACK/DONE. נסגר אוטומטית ומוחזר למקור כאות-כישלון.

## פעולות API
| פעולה | שיטה | נתיב | גוף |
|---|---|---|---|
| פתיחה | POST | `/api/handoffs` | רשומה מלאה ללא `id`/`status` |
| רשימה | GET | `/api/handoffs?status=OPEN&to=<עורק>` | — |
| אישור | PATCH | `/api/handoffs/:id` | `{"status":"ACK"}` |
| סגירה | PATCH | `/api/handoffs/:id` | `{"status":"DONE","closeReason":"..."}` |
| דחייה | PATCH | `/api/handoffs/:id` | `{"status":"REJECTED","closeReason":"..."}` |

## כללי-ברזל תפעוליים
- **אחת-לכל-נושא**: לפני פתיחה, חפש העברה פתוחה עם אותו `subject` ו-`to`. כפילות = רעש.
- **עדות חובה**: העברה בלי `evidence` היא שמועה. קשר לרשומת-שרשרת.
- **יעד מפורש**: `to` חייב להיות עורק קיים. "כולם" אינו יעד.
- **סגירה מנומקת**: `closeReason` קצר אך ספציפי — מה נעשה או למה נדחה.
- **אין סגירה עצמית**: רק היעד סוגר. המקור יכול רק לבטל לפני ACK.

## מדדי-בקרה לקונסולה
- **זמן-תגובה חציוני** מ-OPEN ל-ACK (לפי עורק-יעד).
- **שיעור-סגירה** = DONE / (DONE+REJECTED+EXPIRED) בחלון-זמן.
- **תקועות** = OPEN מעל 24 שעות ללא ACK.
- **עומס-לפי-יעד** = מספר העברות פתוחות לכל עורק (זיהוי צוואר-בקבוק).
- **חזרות** = העברות שנפתחו שוב לאותו נושא אחרי REJECTED.

## דוגמה מלאה
ביקורת מגלה ש-`/api/saos/status` חסר אימות-הרשאות. עורק-הביקורת פותח:
```json
{
  "from": "audit",
  "to": "builder",
  "kind": "FIX",
  "priority": "HIGH",
  "subject": "חסר RBAC על /api/saos/status",
  "evidence": ["ledger:blk-9f2a"],
  "dueBy": "2026-10-24T00:00:00Z"
}
```
עורק-הבנייה מאשר (ACK), מתקן, וסוגר עם `closeReason: "נוסף middleware הרשאות + בדיקה"`. הביקורת רואה DONE ומסוגלת לסגור את הממצא שלה בהפניה להעברה.

## טעויות נפוצות
- פתיחת העברה כ"תזכורת" במקום כהעברת-אחריות — לא ייסגר.
- `closeReason` כללי מדי ("טופל") — חסר ערך-בדיקה.
- שכחת `dueBy` בהעברות HIGH — הן יזדקקו לתזכורת ידנית.
- שימוש ב-`to` לא-קיים — ההעברה תישאר OPEN לנצח.

## צ'ק-ליסט לפני פתיחה
- [ ] חיפשתי העברה פתוחה זהה — לא נמצאה.
- [ ] יש `evidence` מצביע לרשומת-שרשרת.
- [ ] `to` הוא עורק קיים ופעיל.
- [ ] `kind` נבחר נכון (FIX/DECISION/DEPENDENCY/ARTIFACT).
- [ ] `dueBy` מוגדר להעברות HIGH.
