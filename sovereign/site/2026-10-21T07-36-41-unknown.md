# שאלות-ותשובות: אבחון ופתרון כשלים מסוג "unknown" בשרשרת-האמת

> **הקשר**: זוהו 19 כשלים חתומים בשרשרת-האמת המסווגים תחת מחלקה `unknown` — ריכוז חריג המחייב בירור שורש-סיבה ותיקון ממוקד.

---

## ❓ שאלות נפוצות

### 1. מה המשמעות של סיווג `unknown` בשרשרת-האמת?
**תשובה**: סיווג `unknown` מצביע על כשל שמנגנון הסיווג האוטומטי לא הצליח לקטלג לאחת מהקטגוריות המוגדרות (validation, timeout, dependency, permission, resource). זהו **סימפטום** — לא סיבת-שורש. הכשל עצמו נרשם וחתום כהלכה, אך חסר הקשר תפעולי לטיפול.

### 2. איך מזהים אם מדובר בדפוס חוזר או באירועים בודדים?
**תשובה**: בדוק שלושה מאפיינים חוצים:
- **חתימת זמן**: האם הכשלים מרוכזים בחלון זמן צר (שעות/ימים) או מפוזרים?
- **מזהה משימה/עובד**: האם אותו `workerId` או `taskType` חוזר?
- **Hash קלט**: האם אותם תשומות (payload זהה) מייצרות כשל חוזר?

> **כלל אצבע**: אם ≥3 כשלים חולקים 2+ מאפיינים → דפוס מערכתי. אם מפוזרים → כשלים אקראיים.

### 3. מהן סיבות-השורש הנפוצות מאחורי `unknown`?
| סיבה | סימני-זיהוי | בדיקה מהירה |
|-------|-------------|----------------|
| **חריגה לא-מטופלת בקוד עובד** | Stack trace חסר/קטוע בלוג | הרץ `grep -r "unhandled"` בקוד העובד הרלוונטי |
| **תלות חיצונית לא-זמינה** | כשל בזמן קריאה ל-API/DB חיצוני | בדוק לוגי רשת ו-status codes חיצוניים |
| **חריגת משאבים (OOM/CPU)** | כשל ללא שגיאת קוד ברורה | בדוק `memory.heapUsed` ו-`cpu` במדדי העובד בזמן הכשל |
| **מצב מרוץ (race condition)** | כשל לא-דטרמיניסטי באותו קלט | הרץ את המשימה 10× ברצף — אם מצליח לפעמים → race |
| **גרסת קוד לא-תואמת** | כשל מיד לאחר פריסה חדשה | השווה `git log --oneline -5` מול `worker.version` בלוגר |

### 4. איך מחלצים הקשר מכשל `unknown` חתום?
**צעדים מעשיים**:
```bash
# 1. שלוף את רשומת השרשרת המלאה
curl -s /api/ledger/entries?class=unknown&limit=20 | jq '.[] | {hash, timestamp, taskId, workerId, payload, error}'

# 2. הצלב עם לוגי העובד הספציפי
curl -s /api/workers/{workerId}/logs?since={timestamp-5m}&until={timestamp+5m}

# 3. בדוק מדדי סביבה בזמן הכשל
curl -s /api/metrics/snapshot?at={timestamp}&worker={workerId}
```

### 5. מהו תהליך התיקון המומלץ?
**שלב 1 — סיווג רטרואקטיבי** (מיידי):
- סמן כל כשל `unknown` עם תגית סיבה משוערת (`code-bug`, `external-dep`, `resource`, `race`, `version-mismatch`)
- עדכן את הרשומה בשרשרת דרך `PATCH /api/ledger/entries/{hash}/classify`

**שלב 2 — תיקון ממוקד** (לפי סיבה):
| סיבה | פעולת תיקון |
|-------|-------------|
| `code-bug` | תיקון קוד + פריסה חמה לעובד הרלוונטי |
| `external-dep` | הוספת retry/backoff + circuit breaker + התראת ספק |
| `resource` | הגדלת הקצאת זיכרון/CPU או אופטימיזציית קוד |
| `race` | הוספת נעילה/אידמפוטנטיות למקטע הקריטי |
| `version-mismatch` | rollback או forward-fix + אימות גרסה בהפעלה |

**שלב 3 — מניעה** (מתמשך):
- הוסף ולידציית קלט מחמירה בכניסה לעובד
- הטמע `try/catch` גלובלי עם סיווג שגיאה אוטומטי
- הגדר התראה: `alert if unknown_failures_5m > 2`
