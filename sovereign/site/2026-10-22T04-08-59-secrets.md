# לקחים מעשיים: ניהול סודות (Secrets) בסביבת ריבונות אוטונומית

> נכתב בעקבות ממצא "סולם-מוצה: אימות רוטציה וניקוי SOVEREIGN_VAULT_SECRET לאחר דליפה היסטורית" — אך **אינו חוזר על הכותרת** אלא ממצה את הלקח התפעולי הכולל.

---

## 1. עקרונות יסוד
| עיקרון | יישום ב-SAOS |
|----------|--------------|
| **אפס אמון בקוד** | סודות לעולם לא בקוד, לא ב-.env מקומי, לא ב-config-map גלוי |
| **הפרדת הרשאות** | כל רכיב (Worker, Dispatch, Arsenal, Census) מקבל *רק* את הסודות שהוא צורך |
| **רוטציה כברירת-מחדל** | כל סוד פג-תוקף אוטומטית תוך ≤ 30 יום |
| **ביקורת מלאה** | כל גישה/שינוי נרשם ב-Ledger (hash-chain) עם חתימה קריפטוגרפית |
| **התאוששות מהירה** | נוהל "נשימה אחת" לביטול והחלפה תוך < 5 דקות |

---

## 2. ארכיטקטורת כספת (Vault) מומלצת
```
+------------------+     +------------------+     +------------------+
|  SOVEREIGN_VAULT |---->|  PER_COMPONENT   |---->|  RUNTIME_INJECT  |
|  (מקור אמת יחיד) |     |  SCOPED_TOKENS   |     |  (env/fs/mem)    |
+------------------+     +------------------+     +------------------+
        |                        |                        |
        v                        v                        v
  - HSM/KMS backend        - TTL קצר             - zero-disk
  - מדיניות גישה           - scope צר            - ניקוי בזיכרון
  - גיבוי מוצפן            - ביטול מיידי        - אין logs
```

**מימוש מינימלי**: HashiCorp Vault / AWS Secrets Manager / 1Password CLI + sidecar injector.

---

## 3. צ'ק-ליסט תפעולי (Definition of Done לכל סוד)

### יצירה
- [ ] נוצר דרך CLI מאושר (`vault write` / `op item create`) — לא ידני
- [ ] תגיות חובה: `owner`, `component`, `rotation-days`, `severity`
- [ ] מדיניות גישה מוגדרת כ-code (policy-as-code)
- [ ] נרשם ב-Ledger: `SECRET_CREATED {id, component, ttl, hash(policy)}`

### רוטציה (אוטומטית + ידנית)
- [ ] Cron יומי בודק `expires_at < now + 7d` → מייצר גרסה חדשה
- [ ] רוטציה ידנית: `vault rotate <secret-id> --reason="<cause>"`
- [ ] **חובה**: הגרסה הישנה מבוטלת מיידית (`revoke`), לא "מושבתת"
- [ ] נרשם ב-Ledger: `SECRET_ROTATED {old_id, new_id, trigger, operator}`

### דליפה / חשד לדליפה
- [ ] פקודה אחת: `vault emergency-revoke <pattern> --confirm`
- [ ] כל הרכיבים מקבלים סיגנל `SIGHUP` / webhook לטעינה מחדש
- [ ] נרשם ב-Ledger: `SECRET_COMPROMISED {ids, detection_source, action_taken}`
- [ ] Post-mortem תוך 24 שעות → מסמך CONTENT חדש עם לקחים

### ביטול רכיב / Offboarding
- [ ] `vault revoke-component <component-name>` — מבטל *את כל* הסודות של הרכיב
- [ ] ניקוי הזרקות ריצה (restart pods / workers)
- [ ] נרשם ב-Ledger: `COMPONENT_OFFBOARDED {component, revoked_count}`

## 4. אינטגרציה עם משטחי SAOS

| משטח | נקודת חיבור | פעולה נדרשת |
|--------|--------------|--------------|
| **Ledger** | כל אירוע סוד | `POST /api/ledger/append` עם סכימה קבועה |
| **Arsenal** | כלי `vault-cli` | הוספה ל-`/api/arsenal` ככלי רשמי (`kind: secret-ops`)
| **Census** | רישום רכיבים | שדה `secrets_scope` בכל רכיב פעיל |
| **Handoffs** | העברת הקשר | סודות *לא* עוברים ב-handoff — רק `secret_ref` |
| **Dispatch** | משימות רוטציה | Job קבוע `secret-rotation-scan` כל 6 שעות |
| **Metrics** | חשיפה בטוחה | `/api/metrics` כולל `secrets_due_rotation`, `secrets_revoked_24h` |

## 6. תסריטי "יום הדין" (Runbooks)

### תסריט א: דליפת `SOVEREIGN_VAULT_SECRET` (מפתח מאסטר)
1. `vault emergency-revoke sovereign-master --confirm`
2. הפעלת מפתח גיבוי מה-HSM (offline ceremony)
3. רוטציה מפלסית: כל הסודות הנגזרים → חדשים
4. איפוס כל ה-tokens ב-Census → restart כל ה-workers
5. דיווח Ledger: `MASTER_KEY_ROTATED {old_hsm_slot, new_hsm_slot, operator}`
6. עדכון `SOVEREIGN_VAULT_SECRET` ב-CI/CD runners

### תסריט ב: רכיב נפרץ (Worker/Arsenal tool)
1. `vault revoke-component <compromised-component>`
2. בידוד רשתי (network policy deny-all)
3. ניתוח Ledger: אילו סודות ניגש ב-24h אחרונים
4. רוטציה ממוקדת רק לסודות שנחשפו
5. Deploy גרסה נקייה של הרכיב
